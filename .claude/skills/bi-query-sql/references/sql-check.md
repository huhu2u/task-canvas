# SQL 检查（onesql_sqlparser）

> 提供独立的 SQL 语法/语义/成本预检查能力，也作为查询执行前的前置检查步骤。

## 1. 调用方式

```bash
node <skill_dir>/scripts/bin/mcporter.js call 'hive.onesql_sqlparser(mis: "<用户MIS号>", statement: "<SQL语句>")'
```

| 参数 | 必填 | 说明 |
|------|------|------|
| `mis` | ✅ | 用户 MIS 号（获取当前登录用户的mis，或询问用户） |
| `statement` | ✅ | 待检查的 SQL 语句 |

## 2. 结果解读

### 阻断级别（必须修复才能执行）

- `pass` 为 **false** → SQL 存在语法或语义错误
  - 提取错误信息，给出修复建议
  - 如果是用户提供的 SQL → 提示具体问题，建议修正
  - 如果是 Agent 生成的 SQL → 直接修复后重新检查
- `pass` 为 **true** 但**分区表未添加分区条件** → 阻断
  - 提示必须添加分区条件（通常是 `dt` 字段）
  - 帮助用户补充合理的分区范围

### 警告级别（提示但不阻断执行）

| 场景 | 风险 | 建议 |
|------|------|------|
| SQL 超过 10000 字符 | 语句过长，可读性差且可能影响解析性能 | 建议拆分查询或用 CTE 简化 |
| JOIN 超过 5 个 | 查询复杂度高，可能超时 | 建议拆分或优化 |
| 缺少 ON 条件（笛卡尔积） | 数据量爆炸 | **重点警告**，强烈建议修复 |
| 多层嵌套聚合或窗口函数 >3 个 | 性能风险 | 建议简化 |
| 分区范围过大 | 扫描数据量大，耗时长 | 建议缩小范围 |
| 子查询嵌套 >3 层 | 可读性差，优化器难优化 | 建议用 CTE 重写 |

发现警告项 → 输出 ⚠️ 警告列表，告知用户风险。

## 3. 独立使用场景

用户只想检查 SQL 质量（不执行）时：
1. 接收用户的 SQL
2. 调用上述命令检查
3. 输出检查报告：
   - ✅ 通过 / ❌ 未通过
   - 错误详情（如有）
   - ⚠️ 警告列表（如有）
   - 优化建议
